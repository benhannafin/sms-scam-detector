# Learning log

After each stage, write 2–3 sentences in your own words: what the code does, why it's built that way, and anything new you learned. If you can't explain it, ask until you can.

| Stage | What it does and why (my words) |
| --- | --- |
| 0 – Setup | |
| 1 – Data loading and cleaning | `load_dataset()` reads the CSV as UTF-8 and returns only labels and text, with whitespace trimmed and label spelling fixed. It removes every message labelled both spam and smishing, then removes duplicates, because conflicting labels can't teach the model anything and a message in both the training and test sets would inflate the scores (data leakage). I learned to check assumptions against the real file: `latin-1` garbled every £, and leading tabs were hiding most of the duplicates and conflicts, leaving 5,797 messages rather than 5,947. |
| 2 – Text preprocessor | `clean_text()` lowercases a message, removes HTML-style codes, then replaces links, money and phone numbers with `urltoken`, `moneytoken` and `phonetoken`, in that order so that digits in a link aren't mistaken for a phone number. Tokens let the model learn general patterns like "asks you to call a number" instead of treating every number as a rare word, and training and live checks share the function so the model always sees text cleaned the same way. I learned that a dataset can contain accidental giveaways: HTML codes appeared only in ham, so someone could have pasted one into a scam to make it look legitimate. |
| 3 – Training pipeline | `training/train.py` cleans the data, removes repeats, splits it 80/20, uses 5-fold cross-validation on the training set to choose `C` by macro F1, trains TF-IDF + logistic regression, scores it once on the test set and saves the model. The test set stays locked away so the score reflects messages the model has never seen, and `C` limits how much it can rely on any one word, which guards against overfitting. I learned that cleaning can itself create data leakage, because template scams become identical once numbers are tokens, and that an honest 94.9% scam-vs-safe recall, just under the 95% target, is better than an inflated score. |
| 4 – Classifier (+ mock) | `load_model` checks a saved model's checksum, scikit-learn version and type before returning a `Classifier`, and `classify` turns cleaned text into a `Prediction` with a label, a probability per class and a count of recognised terms. The checks exist because some damaged files load normally and give wrong answers, and the mock has the same `classify` method so later tests can set an exact answer without a model file. I learned that a model always answers, even with no evidence: text with no known words came out as 83% ham, so the app needs a way to show Unsure instead of false reassurance. |
| 5 – Explainer | `explain()` picks up to 3 reasons from each term's contribution (TF-IDF value × learned weight), dropping weak terms under 0.15 and terms that overlap one already chosen, then words them plainly, such as "Contains a link". For a Legitimate result it shows only words that pointed towards spam or scam, as signs to be careful of, because citing "my" and "me" as reasons a message is genuine would be false reassurance. I learned that an explanation can be exact and still mislead: the "Hi mum" scam was rated Legitimate, and only showing what looked suspicious keeps the result honest. |
| 6 – Check service | `CheckService.check()` cleans a message, classifies it and explains it, then applies the Unsure rules: no recognised terms is always Unsure, and so is a top probability under 0.7, a placeholder until Stage 11. It's the application layer, so it holds the rules but does no machine learning itself, and it's given its classifier when created (dependency injection), so tests can use the mock. I learned that the order of rules matters: checking for no recognised terms first stops a message the model knows nothing about from looking 83% confident. |
| 7 – REST API | `POST /api/check` takes JSON `{"message": ...}`, checks it's text, not empty and at most 1,000 characters, runs the check service and returns the label, confidence, status and reasons as JSON. `create_app()` loads the model once at startup and gives each app its own rate limiter (20 checks per hour per IP); every error has the same shape and uses status codes such as 400, 429 and 503. I learned that keeping messages out of logs takes care: an unexpected error's text could contain the message, so only the error's type is logged. |
